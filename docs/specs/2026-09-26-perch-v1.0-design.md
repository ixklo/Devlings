# Perch v1.0: design

Status: in progress · Builds on `2026-09-26-perch-v0.2-design.md`. That doc stays the base contract; this one lists v1.0 changes and decisions. Gates and evidence are in `docs/release/v1.0.0.md`.

## 1. Goals

A v1.0.0 that a stranger can download, install, trust, use daily, update and uninstall cleanly:

- Verified on Windows 11.
- Honestly labelled beta on macOS and Linux.
- Free to run: no paid services, no API keys.

## 2. Verified facts (Claude Code 2.1.282, 2026-09-26)

Measured live with a stand-in hook server and tiny `claude -p` runs.

**PermissionRequest hook**
- Fires in `-p` runs with `--permission-prompts none`.
- Payload keys: `session_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `prompt_id`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input`, `permission_suggestions`. There is no `tool_use_id`.
- Bash and PowerShell inputs carry `command` and `description`.
- Example suggestions: `{"type":"setMode","mode":"acceptEdits","destination":"session"}` and `{"type":"addDirectories","directories":[…],"destination":"session"}`.

**Answers to a PermissionRequest**
- `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` runs the tool.
- `"deny"` with a `message` blocks it. The stream shows `system/permission_denied` with `decision_reason_type:"hook"` and the message; Claude may retry another way.
- A 5 s hold before allowing works; the run simply waits.
- A hook that times out gives no decision, so the tool is denied in `-p` ("no approval surface").

**Other flags**
- `--setting-sources user` skips the project's `.claude/settings.json`: its hooks, and presumably its `env`. User-level hooks still run.

**Hooks when Perch isn't running** (connection refused)

| Hook | What the user sees |
|---|---|
| `Stop` over HTTP | `system/notification` "Stop hook error occurred · ctrl+o to see" after every turn. `"async": true` doesn't suppress it. |
| `SessionEnd` over HTTP | "SessionEnd hook [...] failed: connect ECONNREFUSED" on stderr when a session exits. |
| `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest` over HTTP | Nothing, and no added delay. |
| Async command hooks that exit 0 | Nothing. |

**Claude Code's own prompt and the PermissionRequest hook** (measured by emulating the VS Code extension's host protocol: `claude` with `--output-format stream-json --verbose --input-format stream-json --permission-prompt-tool stdio`, plus a PermissionRequest HTTP hook; redacted captures in `src-tauri/tests/fixtures/cc2.1.282_host_*.ndjson`)
- The native prompt and the hook start **at the same moment**. The prompt never waits for the hook.
- If the user answers natively first, that answer applies at once. The pending hook is ignored; its connection stays open until the hook times out or the process exits.
- If the hook answers `allow` first, Claude Code withdraws its own prompt (the host receives `control_cancel_request`) and runs the tool.
- A hook that answers `{}` (no decision), or times out (Claude Code closes the connection), leaves the native prompt working normally.
- In a `-p` run with `--permission-prompts none` and no host, a hook that doesn't decide means the tool is denied.
- `PermissionDenied` fires only for auto-mode denials, never when a user denies a prompt.

**Host protocol**
- Request (stdout): `{"type":"control_request","request_id":"…","request":{"subtype":"can_use_tool","tool_name","display_name","input","description","permission_suggestions","blocked_path","decision_reason_type","tool_use_id"}}`.
- Answer (stdin): `{"type":"control_response","response":{"subtype":"success","request_id":"…","response":{"behavior":"allow","updatedInput":<input>[,"updatedPermissions":[…]]}}}`, or `"response":{"behavior":"deny","message":"…"}`.
- Withdrawal (stdout): `{"type":"control_cancel_request","request_id":"…"}`.
- The prompt goes in as one line, `{"type":"user","message":{"role":"user","content":"…"}}`; after the `result`, closing stdin ends the process.
- Permission updates (`addRules`, `setMode`, `addDirectories`, …, each with a `destination` of `session`, `localSettings`, `projectSettings` or `userSettings`) can be echoed from `permission_suggestions` into `updatedPermissions`, in a hook decision or a host answer.

## 3. Hook entries (v1)

All entries point at Perch's localhost server with the existing 64-hex token.

| Event | Handler | Why |
|---|---|---|
| SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Notification, PermissionDenied | `http`, timeout 2 | Silent when Perch is down, and no spawn cost on frequent events |
| PermissionRequest | `http`, timeout 300 | Sync decision. Perch always answers before its own hold ends (at most 240 s, D2). |
| Stop, StopFailure, SessionEnd | `command`, `async: true`: `"<perch exe>" --hook-relay <port> <token>` | HTTP versions show error noise when Perch is quit (§2). The relay posts stdin to Perch and always exits 0 within ~1 s. |

Each entry is its own group, exactly:

```json
{ "hooks": [ { "type": "http", "url": "http://127.0.0.1:<port>/hook/<token>", "timeout": 2 } ] }
{ "hooks": [ { "type": "http", "url": "http://127.0.0.1:<port>/hook/<token>", "timeout": 300 } ] }
{ "hooks": [ { "type": "command", "command": "\"<perch exe>\" --hook-relay <port> <token>", "async": true } ] }
```

- **Identification.** An entry is Perch's if its URL matches `http://127.0.0.1:<port>/hook/<64 hex>`, or its command contains `--hook-relay <port> <64 hex>`. Uninstall removes exactly those hook objects (and only the groups, event keys and `hooks` object that become empty because of it); everything else keeps its value.
- **Status.** `current` when Perch's hook objects mean the same as the 11 above; `outdated` when any Perch entry exists but the set differs; `not installed` otherwise. Only `current` counts as installed.
  - "Mean the same" compares each entry's event, `type`, `url` or `command`, `timeout` as a number (so `2` and `2.0` match) and `async` (missing means false).
  - Key order and extra fields don't count.
- **Migration.** On launch, if hooks are `outdated` (for example, v0.2's 7 HTTP entries, an earlier v1 PermissionRequest entry with timeout 75, another port, or a moved executable), reinstall once with the usual backup. Perch never rewrites the file on every start or quit. It doesn't migrate at all while running from a temporary location (see below).
- **Relay path.** The relay uses `std::env::current_exe()`, so a dev build installs dev paths. QA always reinstalls from the installed build. In a Linux AppImage it uses `$APPIMAGE` (the mount path changes every launch). The path is only double-quoted, never escaped. Stop, StopFailure and SessionEnd fall back to `http`, timeout 2 (like the other HTTP entries) when the path can't be used:
  - **Temporary location:** the path contains `/AppTranslocation/` (macOS App Translocation) or starts with `/Volumes/` (run from a mounted disk image). It would be gone after this run. Existing hooks aren't migrated, a fresh install uses the HTTP fallback, a warning is logged, and `setup.setupHint` says to move Perch to Applications.
  - **Shell characters:** the path contains `$`, `` ` ``, `"`, `%`, `!` or a control character, or a `\` outside Windows. bash and cmd expand these differently inside double quotes. A warning is logged.
  - Once a usable path exists, the HTTP fallback counts as `outdated` and is migrated to the relay.
- **Relay behavior.** Reads stdin (at most 4 MB, the hook server's cap; larger bodies are dropped), POSTs it to `http://127.0.0.1:<port>/hook/<token>` with 1 s connect, write and read timeouts, prints nothing, and always exits 0. A watchdog ends it after 5 s even if stdin never closes. Malformed arguments exit 0 without sending.
- **settings.json writes.** Written to `settings.json.perch-tmp` and renamed over the file. If the file changed between Perch's read and its write, Perch starts over from the new content, up to 3 times, then gives up with a message. Invalid JSON or invalid UTF-8 is never rewritten. A backup `settings.json.perch-backup-<epoch s>[-n]` is saved before each change. Old backups are pruned to the newest 5 only after the new file is in place. If the rename fails, the temp file and the new backup are removed and nothing is pruned. A symlinked settings.json stays a symlink (its target is replaced), and on Unix the new file and backup keep the original's permissions.

**Hook server.** `POST /hook/<token>` on 127.0.0.1. The token is compared in constant time. Every response is `Content-Type: application/json`: 404 for a wrong path or method, 503 when too many are in flight, otherwise 200.
- **Workers.** Each request is read on its own worker thread, at most 32 at once (beyond that it answers 503 at once). A PermissionRequest gives its slot back before its handler runs, so held requests never take slots from other hooks; the approvals layer bounds holds itself (at most 16, D3).
- **Events.** Every body except PermissionRequest is answered `{}` immediately. Every body, PermissionRequest included, is applied on one processing thread in arrival order (requests are numbered as they arrive and applied in that order), so a PermissionRequest's "needs input" lands in order with the session's other events. A request whose body stalls holds later events back for at most 2 s; if it arrives after that, its event is dropped. The backend's `on_event: FnMut(Value) + Send` runs there.
- **PermissionRequest.** Calls `on_permission: Fn(Value) -> String + Send + Sync` on its worker, and the return value is the response (empty or a panic means `{}`). It may block while Perch holds the request (D3); a held request never delays other events.
- **Size.** Bodies up to 4 MB are read. A larger body is drained, answered 200 `{}` and ignored (logged at debug). Size never causes an error answer, because Claude Code would show one as a hook error.
- **Late events.** After SessionEnd, the session's late events (a Stop relayed after its SessionEnd by a separate process, steps, needs-input) are ignored for 10 s. UserPromptSubmit or SessionStart (a resumed session) clears that at once.

## 4. Contract changes

**Config keys** (new, in `config.json`, all with defaults)

| Key | Default | Purpose |
|---|---|---|
| `autoUpdate` | `true` | Check for updates at launch and daily |
| `lastUpdateCheck` | `null` | Epoch ms of the last successful check (update found or none newer), automatic or manual |
| `watchApprovals` | `false` | Answer permission requests of watched sessions from the pet (D3) |
| `approvalHoldSecs` | `60` | How long a watched request is held for an answer in the pet: 30, 60, 120 or 240 (anything else reads as 60) |
| `approvalsIntroSeen` | `false` | The one-time intro card was answered; finishing onboarding also sets it |
| `diagnosticsLevel` | `"info"` | Log level: `off`, `error`, `warn`, `info`, `debug` or `trace`, any case (anything else reads as `info`). Read at startup. |

**projects.json.** `ProjectEntry.trusted: bool`: trusted in Perch (D6). Default `false`; files without it load as `false`.

**Snapshot additions**
- `setup.setupHint: string | null`: advice that doesn't block setup and doesn't set `needsSetup`. Today the only hint is "Move Perch to Applications and open it from there…", shown while Perch runs from a temporary location.
- `update: UpdateStatus`, where `{ state: "idle"|"checking"|"available"|"downloading"|"ready"|"error"|"disabled", version?, notes?, progress?, error? }`.
  - Unset fields are left out of the JSON.
  - `progress` is a whole percent (0–100) while downloading; absent when the server sends no size.
  - `error` is set for `error` (a short message, see D13) and for `disabled`, which means a development build without `PERCH_UPDATE_ENDPOINT` ("Updates are off in development builds.").
- `approvals: PendingApproval[]`, oldest first, where `{ id, sessionId, project, projectName, source: "watch"|"ask", toolName, rawToolName|null, summary, description|null, details, lossy, tooLong, risks, canAlwaysAllow, alwaysLabel|null, alwaysDetail|null, expiresAt|null }`.
  - `id` is 128 random bits in hex. `toolName` is Claude Code's `display_name` when it sends one.
  - `summary` is the exact `command`, `file_path`, `notebook_path`, `url`, `path` or `pattern` from the tool input (the first present, capped at 4000 characters), else the input as compact JSON cut to 300 characters.
  - `description` is Claude's description of the call (the request's `description`, else the input's), or null.
  - `rawToolName` is Claude Code's own name for an `mcp__*` tool shown under a different `display_name`, else null.
  - `details` is the whole `tool_input` as pretty JSON (so a Write's content and an Edit's old and new strings), cut at 16 KB.
  - `lossy` is true when the headline doesn't cover what is being approved: a tool Perch doesn't know (anything outside Bash, PowerShell, Read, Write, Edit, MultiEdit, NotebookEdit, WebFetch, WebSearch, Glob and Grep, so every MCP tool), a key outside the tool's normal shape with a non-trivial value (not null, false or ""), a headline that had to be cut, or `tooLong`.
  - `tooLong` is true when `details` had to be cut or the exact command/path/URL is over 4000 characters. Such a request can only be denied: the card has no Allow or Always, and `answer_approval` refuses them. (A JSON preview headline cut at 300 characters only makes it `lossy`, since Details shows the whole input.)
  - `risks` are short warnings for risky flags; today "Runs outside the sandbox" for `dangerouslyDisableSandbox: true`.
  - `canAlwaysAllow` is true when a suggestion survives the filter: well-formed `addRules` (behavior `allow`) and `addDirectories` with a known destination, and `setMode` only to `acceptEdits`, `default` or `plan` with destination `session` (so never `bypassPermissions`). `alwaysLabel` is "Allow for this session" when every kept suggestion's destination is `session`, else "Always allow". `alwaysDetail` says what it does in one line, e.g. "Adds the rule Bash(npm test:*) to this project's local settings", "Lets Claude Code edit files for the rest of this session", "Adds C:\proj as a working folder for this session".
  - `expiresAt` is epoch ms when a watch hold ends, and `null` for Ask requests, which wait until answered, withdrawn, the run ends, or 10 minutes pass.
  - Any pending approval makes `petState` `needs_input` (setup still wins).

**Commands (new)**

| Command | What it does |
|---|---|
| `check_for_update` | Manual check. Returns UpdateStatus once the check is done; a found update keeps downloading in the background. While a check or download is running, or updates are disabled, it just returns the current status. While `ready` it still checks, quietly (see D13). |
| `install_update` | Refused while an Ask run is active ("Finish or stop the running ask first.") or before an update is ready; otherwise installs and relaunches. `ask` refuses once an install has begun. |
| `set_auto_update {enabled}` | Returns Snapshot |
| `answer_approval {id, decision: "allow"\|"deny"\|"always"}` | Answers a pending request: the hook's decision JSON or the Ask's control_response. Deny sends the message "The user declined this in Perch."; always echoes the kept suggestions as `updatedPermissions`. The first answer wins; a later one, an unknown or expired id, or "always" without a kept suggestion is a harmless error. Returns Snapshot. |
| `set_watch_approvals {enabled}` | Saves `watchApprovals`; turning it off answers every held request `{}`. Returns Snapshot. |
| `set_approval_hold {secs}` | `secs` must be 30, 60, 120 or 240, else an error. Applies to new requests. Returns Snapshot. |
| `mark_approvals_intro_seen` | Returns Snapshot |
| `trust_project {project}` | Sets `trusted: true` on a known project (else "Unknown project.") and saves `projects.json` atomically (temp file, then rename); a change that can't be saved is undone and returned as an error. Returns Snapshot. |
| `untrust_project {project}` | The reverse: `trusted: false`. Returns Snapshot. |
| `get_diagnostics` | Returns a string: app version, OS and arch, Claude Code version, path and how it was found, login check, hook status, hook server port or error, settings and log paths, and the last 200 log lines. The hook token (and any 64-hex run) reads `<token>` and the home folder reads `~`. |
| `open_log_folder` | Creates the log folder if needed and opens it in the file manager |

**Events.** No new event names; everything rides on `snapshot`, except the untrusted-folder notice (D6), which rides on `pet-event` like the rest of an Ask's chat:
- New `Kind` `untrusted`, Ask only: `label` is the headline, `text` the "Skipped: …" sentence, `sessionId` the conversation's id (empty for a new chat, whose id isn't known yet).
- Sent once per run, after the process starts and before any of its output. It never changes a thread or the snapshot.
- The frontend adds it to the mini chat as `ChatTurn { role: "untrusted", text: <headline>, detail: <skipped> }`. It isn't in the transcript, so it's gone once the conversation reloads.

**CLI.** `perch --uninstall-hooks` (headless: remove hooks from `$CLAUDE_CONFIG_DIR` or `~/.claude` `settings.json`, then the start-at-login entry: the HKCU `Run` and `StartupApproved\Run` values named `Perch` via a hidden `reg delete` on Windows, `~/Library/LaunchAgents/Perch.plist` on macOS, `~/.config/autostart/Perch.desktop` on Linux; exits 0, or 1 if settings.json couldn't be updated) and `perch --hook-relay <port> <token>` (headless relay, see §3; always exits 0). Both are handled at the very top of `run()`, before any Tauri or single-instance setup, so a running Perch never sees them. `--hook-relay` wins if both appear.

## 5. UI states (new)

**Cards**
- **Update ready.** "Perch <version> is ready. Restart to install." with Restart and Later. Only shown when no Ask run is active. Later hides it until the next launch or a newer version. Sits above the thread cards.
- **Approval.** Project, tool (with `rawToolName` under it for MCP tools), `risks` badges, the exact command/file/URL in monospace (wrapping, selectable), Claude's description, a **Details** disclosure with `details` in a scrollable monospace block (open by default when `lossy`), and buttons **Deny** / **Allow**, plus the always button (`alwaysLabel`) only when `canAlwaysAllow`, with `alwaysDetail` shown in a line under the buttons (also its tooltip and accessible description).
  - **Arming.** The buttons are inert (faded, `aria-disabled`) until they have been visible and in the same place for 800 ms, so a card that just appeared, is still animating in, or slid into another card's place can't take a click meant for something else. Any move disarms them again: their position is re-checked every 100 ms and after every render, and the cards flipping or shifting (`pet-placement`) or the window moving disarms them at once. A mouse click counts only when its pointerdown also came after arming; a keyboard press on a deliberately focused button counts once armed.
  - Nothing is focused by default, Enter is never bound to Allow, and no keyboard shortcut answers anything. The buttons are real buttons; after the first click all three are disabled.
  - `tooLong`: only **Deny**, with "Too long to review here. Answer in Claude Code." (Ask: "Too long to review here, so it can only be denied.").
  - When a request leaves (answered, expired, resolved elsewhere), a placeholder of the same height ("Answered" or "No longer waiting") keeps its place for 1.2 s, so the next card doesn't slide under the cursor; it absorbs clicks.
  - A watched request shows a thin countdown bar to `expiresAt`. One card per request, nearest the pet, standing in for that session's thread card; when the hold ends the plain "needs input" card comes back. At most two approval cards (three cards in all) show before "+N more". Collapsing the cards hides them too.
- **Approvals intro** (once, after upgrading: `approvalsIntroSeen` false, hooks installed, onboarding already finished). "{pet} can answer permission prompts. When a Claude Code session asks to run something, you can Allow or Deny it right here. Claude Code's own prompt still works too." with **Turn on** (sets `watchApprovals`, marks it seen) and **Not now** (marks it seen).

**Pet.** The waiting animation while any approval is pending.

**Mini chat.** Inline approval rows for the open Ask, above the reply box, with the same buttons and rules (arming, Details, too-long, placeholders); the header says "Needs you" while one waits. A question (AskUserQuestion) or a plan (ExitPlanMode) never becomes a row: it is denied with a message Claude can act on and a note appears in the chat instead (D4). Stop and New chat deny them ("Stopped in Perch." / "The user started a new chat in Perch.") and they disappear. The untrusted-folder notice is a distinct system row (not Claude's text), once per run: the headline, what was skipped, and **Trust this folder in {pet}**. Once the folder is trusted, every such row in the chat reads "Trusted in {pet}. The next Ask uses this folder's settings." with a **Stop trusting** link.

**Settings**
- Approvals: "Answer permission prompts from {pet}" (with a line that Claude Code's own prompt stays available) and "Keep a request open for" 30 s / 1 min / 2 min / 4 min.
- Trusted folders (only while there is one): each folder trusted in Perch, its path, and **Stop trusting**.
- About: current version; "Check for updates automatically" toggle; "Check for updates" with an inline status (checking, up to date, available, downloading x%, ready with "Restart to update", couldn't check); Copy diagnostics (with a "Copied" confirmation); Open log folder; third-party licenses (`THIRD_PARTY_NOTICES.md` on GitHub).

## 6. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Hook relay (async command) only for Stop, StopFailure and SessionEnd | These were the only noisy events measured; HTTP stays on frequent events, so there's no per-tool-call process spawn |
| D2 | PermissionRequest over HTTP with timeout 300. Installs with 75 migrate through the usual outdated path. Perch always answers before its own hold ends, and holds are at most 240 s. | Silent when Perch is down; Perch always answers before Claude Code gives up |
| D3 | **Watch approvals** (other Claude Code sessions), opt-in via `watchApprovals` (off by default). A PermissionRequest from one of Perch's own Ask sessions (a known Ask `session_id`) is answered `{}` at once, since Asks use the host protocol (D4). With the feature off it is answered `{}` at once too. A question or plan dialog (AskUserQuestion, ExitPlanMode) is answered `{}` at once and kept as a marker (the thread shows "Has a question for you" / "Has a plan for you to review"), so Claude Code's own dialog handles it; it never gets a generic Allow. Otherwise Perch registers a pending approval and holds the HTTP response until (a) the user clicks in Perch: the decision; (b) it's resolved elsewhere (D5): `{}`; (c) `approvalHoldSecs` passes: `{}`, and the card falls back to the plain "needs input" card; (d) the feature is turned off, an update installs, or Perch quits: `{}` to everything pending. At most 16 holds at once (beyond that, `{}` at once), and held requests don't take the hook server's worker slots. The on/off flag lives in the approvals registry, so turning it off and a new request are decided under one lock; turning it on also marks the intro seen. There is no foreground-window detection. With the feature on, a headless run of another tool (`claude -p` without a host) that needs permission waits up to `approvalHoldSecs` for an answer in Perch, and without one Claude Code denies the tool, as it would with no hook. | Measured (§2): Claude Code's own prompt starts with the hook and never waits for it, so nobody ever waits on Perch; an early `allow` withdraws the native prompt, and `{}` or a timeout leaves it working. |
| D4 | **Ask approvals** (on, no setting). Ask runs use the host protocol: `--input-format stream-json --permission-prompt-tool stdio` instead of `--permission-prompts none`, everything else unchanged (`--include-partial-messages`, `--resume`, and M4's `extra_args` last). The prompt is one JSON-encoded user message; stdin stays open behind a writer thread. A `can_use_tool` request becomes a pending approval (source `ask`, no countdown) answered with a control_response when the user clicks; `control_cancel_request` drops it; any other control request gets `{"subtype":"error","request_id":…,"error":"unsupported"}`; the `result` closes stdin so the process exits. Stop, New chat and quit deny the run's pending requests with a short message, then do what they do today. An Ask request unanswered for 10 minutes is denied with "No answer in Perch.". A question (AskUserQuestion) is denied at once with "Perch can't show questions yet. Make a reasonable assumption and say what you assumed." and a plan (ExitPlanMode) with "The user will review the plan in Perch's chat.", each with a note in the chat. Stdin is closed whenever the output reader ends (a result, a money-guard kill, end of output or a read error) and again before Perch waits for the process, so a broken pipe can't hang an Ask. The money guard is unchanged: the same `hidden_command`, the init `apiKeySource` check and the overage kill; an Ask retried after re-locating Claude Code (M9) must pass a fresh login check before the new binary runs. | Without an approval surface, a `-p` run just denies the tool; the host protocol is what the VS Code extension uses. |
| D5 | **Needs input and clearing.** A PermissionRequest (watch, whether the feature is on or off) or a `can_use_tool` (Ask) puts that thread in "needs input" immediately. A watched request, answerable or not, is cleared when the same session sends PostToolUse or PostToolUseFailure with the same `tool_name` and an equal `tool_input` (there is no `tool_use_id`); if none matches exactly, the session's oldest request for that tool (the input may come back with defaults filled in). Also by PermissionDenied with the same tool, or UserPromptSubmit, Stop, StopFailure or SessionEnd (all of that session's requests); a held one is answered `{}`. While any of a session's requests is waiting, its Prompt, Step or reply events (a parallel subagent's tool call, say) update the thread's label but keep "needs input"; UserPromptSubmit clears the requests first, so it resets as usual. Once none are waiting, a tool that ran or was denied puts the thread back to working; so does an answer from Perch (Allow: the tool's step label; Deny: "Declined: <tool>"). | Instant signal, cleared when the request is answered anywhere, and not lost to other activity in the same session. |
| D6 | **Untrusted folders for Ask** (`trust.rs`, decided in the `ask` command at every Ask). **(1) Trusted by Claude Code:** `projects[K].hasTrustDialogAccepted == true` in `$CLAUDE_CONFIG_DIR/.claude.json`, else `~/.claude.json`, for a key K with the folder at or under K. Inside a git repository (nearest `.git` folder or file, root R), K must also be at or under R: the repository root or a folder inside it. A trusted home or projects folder doesn't cover a repository cloned under it, and an outer repository's key doesn't cover a nested one (a submodule or worktree), matching Claude Code, which shows the trust dialog for a nested repository. Outside any repository, any parent counts. The file is read fresh each Ask, read-only, at most 32 MB. Keys and paths match whole component by component (`C:/p/proj` doesn't trust `C:/p/proj2`) and ignore a trailing separator; on Windows also case and `\` vs `/`, with a verbatim prefix removed (`\\?\C:\x` is `C:/x`, `\\?\UNC\server\share` is `//server/share`). A missing, unreadable, oversized or malformed file means "not trusted", never an error. **(2) Trusted in Perch:** `ProjectEntry.trusted`, per project folder (exact path). **(3) What it would run:** the folder and, inside a git repository (nearest `.git` folder or file), the repository root: hook event names, `env` key names (never values) and helper keys (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`, any other `*Helper`) in `.claude/settings.json` and `.claude/settings.local.json`; server names in `.mcp.json`'s `mcpServers`; the number of folders in `.claude/skills/`. At most 1 MB per file; a file that isn't a regular file, is bigger, or doesn't parse to an object lists as "project settings (couldn't be read)". The user's own settings folder (`$CLAUDE_CONFIG_DIR` or `~/.claude`, e.g. when asking in the home folder) never counts as a project's `.claude`. **(4) Decision:** trusted either way, or nothing found (no `.claude` folder and no `.mcp.json` in either place): normal flags, no notice. Otherwise `--setting-sources user` (appended through `AskRequest.extra_args`, after every other flag) and a notice (§4 Events): "This folder isn't trusted in Claude Code yet, so {pet} ran without its project settings. Skipped: hooks (PreToolUse, Stop) · environment variables (ANTHROPIC_BASE_URL, FOO) · MCP servers (db, github) · apiKeyHelper · 2 project skills." Names are sorted, at most 6 per kind then "+N more", without control characters and cut to 40 characters; with nothing specific it says "project settings". **(5) Trust and undo:** the notice's **Trust this folder in {pet}** calls `trust_project`; the next Ask uses the folder's settings. Undo with **Stop trusting** on the same row or in Settings → Trusted folders (`untrust_project`). ## 7. Deferred (with reasons)

- **Replying into live VS Code or terminal sessions.** Channels are a research preview, and concurrent use is risky.
- **Paid signing or notarization.** Money rule. Free OSS code signing (e.g. SignPath Foundation) is an optional step for the owner.
- **Driving the interactive terminal dialog directly.** Needs keystroke injection while the owner uses the machine. The prompt-versus-hook timing was measured through the host protocol the VS Code extension uses (§2); the design doesn't depend on the terminal dialog behaving differently, because nobody waits on Perch.
- **Not in v1.0:** voice input, hatching pets from images, per-monitor pets, i18n, Claude Code plugin packaging.
