# Devlings v1.1: the rename

Status: in progress · Builds on `2026-09-26-perch-v1.0-design.md`, which stays the contract for everything this doc doesn't change. The app was called Perch up to 1.0; the v0.1, v0.2 and v1.0 docs keep that name as history.

## 1. What changes

The app is now called **Devlings**, with the tagline "Desktop pets for Claude Code". Saying it works with Claude Code is fine; "Claude" is never part of the name, and "not affiliated with Anthropic" stays. The repository is `ixklo/devlings`.

The teal bird keeps its name: **Perch** is still a bundled pet and still the default (`store::DEFAULT_PET_NAME`, pet id `perch`). Only the app is renamed.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D22.1 | **User-facing name "Devlings".** `tauri.conf.json`: `productName` "Devlings", `mainBinaryName` "devlings", both window titles "Devlings" (the settings page sets "Devlings Settings"). Installers follow Tauri's naming: `Devlings_<v>_x64-setup.exe`, `Devlings_<v>_universal.dmg`, `Devlings_<v>_amd64.AppImage` and `.deb`, and the macOS updater bundle `Devlings_universal.app.tar.gz`, each with its `.sig` (v1.0.0's assets were the same names with `Perch`). `scripts/gen-latest-json.mjs` classifies artifacts by extension only (`.exe`/`.msi`, `.app.tar.gz`, `.deb`, `appimage`), so it needs no change; only its `notes` text now says Devlings. The start-at-login entry is named after the product (`HKCU\…\Run` value "Devlings", `Devlings.plist`, `Devlings.desktop`); `cli::AUTOSTART_NAME` is pinned to `productName` by a test. | The name users see everywhere |
| D22.2 | **The app identifier stays `io.github.perchpet.perch`.** | It names the app-data folders (config, projects, logs, WebView2 profile), the single-instance lock and the Windows notification app ID. Keeping it means settings, pet, projects, hook port and token carry over with no migration code, and toasts keep working. Users never see it. |
| D22.3 | **Updater endpoint** `https://github.com/ixklo/devlings/releases/latest/download/latest.json`. The override is `DEVLINGS_UPDATE_ENDPOINT`; `PERCH_UPDATE_ENDPOINT` is still read when it isn't set (a blank value counts as unset; `updater::pick_endpoint_var`). Same signing key. | Perch 1.0 installs keep finding updates through GitHub's redirects from the old repository URL, and RC testers' scripts keep working |
| D22.4 | **Windows upgrade from Perch.** With a new `productName`, Tauri's installer treats Devlings as a new app in a new folder (`%LOCALAPPDATA%\Devlings`) with a new uninstall entry. `src-tauri/windows/installer.nsh`'s `NSIS_HOOK_PREINSTALL` removes an existing Perch install first: (1) find it by `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\Perch`'s `InstallLocation`, else the folder Tauri saved in `HKCU\Software\<manufacturer>\Perch`, else `%LOCALAPPDATA%\Perch`, counting it only if `uninstall.exe` is there; (2) close a running `perch.exe` (Tauri's own check only looks for `devlings.exe`), asking first in a normal install and not in a passive or silent one; (3) run `uninstall.exe /S /UPDATE _?=<folder>` and wait: update mode makes Perch 1.0's own hook skip `--uninstall-hooks`, silent mode never offers to delete app data, and `_?=` runs it in place so `ExecWait` really waits; then delete the leftover `uninstall.exe`, the folder if empty, and `HKCU\Software\<manufacturer>\Perch`; (4) delete the `Run` and `StartupApproved\Run` values named "Perch", and Perch's Start menu and desktop shortcuts when they point at the removed `perch.exe` (update mode keeps all of these). The app-data folders are never touched. If the uninstaller fails, a normal install says so and carries on; start-at-login is still removed so the two never both start. `NSIS_HOOK_POSTINSTALL`: when Perch 1.0's in-app updater ran the installer (`/UPDATE`, which skips creating shortcuts), Devlings creates its Start menu shortcut, which registers the notification app ID, and a desktop shortcut if Perch had one, using the template's own functions. On first launch the existing code finishes the move: `migrate_hooks` sees the relay command's executable changed from `perch.exe` to `devlings.exe`, which counts as `outdated` (v1.0 §3), and rewrites the entries once with a backup (unit test `hooks_from_perch_migrate_to_the_devlings_exe`); `restore_launch_at_login` re-adds start-at-login under the new name because the config says it's on. The Devlings uninstaller's `--uninstall-hooks` removes the hooks and the "Devlings" start-at-login entry; nothing there depends on the old name. | One install over the top, or Perch's own update, and nothing of Perch is left running or pointing at a missing program |
| D22.5 | **macOS and Linux upgrade:** the bundle and package names change, so Perch.app, the `perch` .deb and a Perch AppImage stay installed alongside Devlings. The README ("Upgrading from Perch") and the release notes say to delete Perch.app or run `sudo apt remove perch` (or delete the AppImage), plus Perch's own login item if it had one. Nothing is automated for the betas. Settings carry over (D22.2), hooks migrate on first launch (D22.4), and while both are installed the shared single-instance lock means only one runs. | Beta platforms; no installer hook to run |
| D22.6 | **Internal names stay:** the crate (`perch`, `perch_lib`), the Cargo binary name (`cargo build`, `cargo test` and `tauri dev` make `perch.exe`; `tauri build` renames it to `devlings`, so CI's smoke test runs `target/debug/devlings`), Rust modules and function names, test names, the pet source value `"perch"` (the app's own pets folder in `list_pets`), the tray id, thread names and the update-bundle prefix in the cache folder. Everything a user or contributor reads says Devlings: UI text, the tray tooltip, About, CLI messages, log lines ("Devlings 1.1.0 starting on windows x86_64"), the diagnostics header, the answers Devlings sends Claude Code ("The user declined this in Devlings."), docs and templates. The log file is now `devlings.log` (old `perch*.log` files in the same folder are left alone and not read), and `settings.json` backups are `settings.json.devlings-backup-<epoch s>[-n]` written through `settings.json.devlings-tmp`; earlier `settings.json.perch-backup-*` files still count toward the newest 5, so they're pruned in turn. `src-tauri/tests/app_name.rs` and `src/appName.test.ts` fail on "Perch" (or the old repository owner) in any Rust string literal or frontend source line outside an explicit allow-list of the bird's own data. | Not user-facing, and renaming them would churn the code for nothing |
| D22.7 | **The hidden-threads count moves off the pet.** With the cards collapsed there's no badge on the sprite any more; a count pill (`CountPill`) takes the hidden cards' place in the bubble stack: after the setup card, before the update card, in the same flow, so it follows `cardsBelow` and `shiftX` like the cards and is gone while the composer or a thread is open. It shows when collapsing hides a thread or a permission request. Tone and text keep the badge's precedence: "1 needs you" / "2 need you" in amber (`--wait`, `--on-wait`, with a dot), counting needs-input threads plus pending requests, a session with a request once; else "1 blocked" on `--err-ink` with `--on-color`, the cards' own "Blocked"; else "1 thread" / "2 threads" in the `.more-pill` style. Each has a chevron-up. It's a `.more-pill`-sized button with `aria-expanded="false"`, a full name ("2 threads hidden, 1 needs you. Show threads."), a `data-hit` region and the pills' focus halo, a Tab stop in the cards' place before the pet. A click, Enter or Space does what the chevron's "Show threads" does; a pill that held focus hands it to the pet as it goes. While the pill sits nearest the pet, the update card above it has no tail. | Every pet draws its thought puff and "?" at the sprite's top right, where the badge sat, so the badge covered the pet's own bubble exactly when the count mattered. Of the mockup's options the owner chose this one: the hidden cards fold into a pill where they were |
| D22.8 | **A watched session belongs to the folder it started in.** Hook bodies carry the session's current `cwd`, which moves whenever Claude Code changes into a subfolder; Devlings used it as the project, so every subfolder a session visited became a project in the list and the session's card was renamed after it. Claude Code keeps each transcript under `<config>/projects/<start folder with every character but ASCII letters and digits as '-'>/`, so `normalize::session_root` walks up from `cwd` to the folder whose encoded path names one of the transcript's folders (case-insensitively; one `-` per UTF-16 unit, as Claude Code encodes). When none matches (the session left its start folder, or Claude Code shortened a very long name) it keeps `cwd`, as before. Thread cards, the project list and permission cards all use it (`normalize::project_of`). Existing project entries are left as they are: nothing tells a visited subfolder from one the user added. | Found by running [aftershock](https://github.com/ixklo/aftershock) over the repository: `fbe11ef` had filtered temp folders out of the project list, and the same list was still collecting every subfolder a session visited |
| D22.9 | **One plain-text rule for Claude's replies on cards and in notifications.** `plainLine` (cards, TypeScript) and `threads::plain_line` (notifications, Rust) keep code spans as written, turn links into their text, remove heading/quote/list markers, and remove emphasis markers only where they wrap words: the opening marker isn't preceded by a letter, digit or `_`, the closing one isn't followed by one. Before, cards turned `get_user_id` into `getuserid`, `my_file_name.rs` into `myfilename.rs` and `2*3*4` into `234`, and notifications showed the raw Markdown. The TypeScript pattern catches the preceding character in a group instead of a lookbehind, which older WebKit can't parse. | Same review: `1f10946` added the card rule and dropped underscores in the process; notifications never got it |

## 3. What this doc changes in v1.0

- §3 settings.json writes: the temp file and backups are named as in D22.6.
- §4 Snapshot, D7, D13: the endpoint and override variable are as in D22.3.
- §4 CLI: `devlings --uninstall-hooks` and `devlings --hook-relay <port> <token>` (the installed binary), removing the start-at-login entries named "Devlings".
- §5 cards and announcements: "Devlings <version> is ready. Restart to install.", "Devlings needs setup", "Finish setting up Devlings".
- D8: the log file is `<app log dir>/devlings.log`.
- D11: the uninstall hook runs `devlings.exe --uninstall-hooks`; D22.4 adds the pre- and post-install hooks.
- §5 and D20 (and v0.2 §6's "count badge on the pet"): collapsed cards leave the count pill of D22.7 in their place, never a badge on the pet. `--on-wait` and `--err-ink` colour that pill, which gets the pills' focus halo and is a Tab stop where the cards would be.
